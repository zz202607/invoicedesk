# 技术决策（ADR）

> 只追加，不重写历史。每条写清楚：背景、决定、替代方案、什么条件下重新评估。

## ADR-001 桌面技术栈：pywebview + 本地 Web UI

- **背景**：需要“好看、好用、单机、可打包 exe”的 Windows 工具；维护者主要用 Python。
- **决定**：Python 3.13 + pywebview（WebView2）+ Vue 3 + Tabulator + ECharts；前端依赖全部本地化，无 Node 构建。前端组件分期见 ADR-012。
- **替代**：Electron（体积大、需 Node）；PySide6/Qt（界面质感与开发速度不如 Web）；NiceGUI（定制表格交互受限）。
- **重新评估**：WebView2 在目标机器缺失且无法安装；或前端复杂度超出无构建方案；或打包体积失控。

## ADR-002 全本地离线，不接云端识别

- **背景**：发票含公司、税号、金额、行程等敏感财务数据。
- **决定**：解析、存储、导出全部本地；App 内不调用任何云端大模型/OCR。AI 审查流水线只审查代码 diff。
- **替代**：云端 OCR/LLM 提取（精度可能更高，但隐私与成本不可控）。
- **重新评估**：用户明确接受上传脱敏片段，且本地准确率长期不达标。

## ADR-003 双核模型：发票池 + 报销单

- **背景**：实际要交的是《费用报销支出明细表》，其中大量里程、餐费、工资行没有发票；只做发票汇总无法替代人工。
- **决定**：发票与报销行分开建模；一行可关联 0..n 张发票；无票行是一等公民。
- **替代**：一张发票 = 一条报销行（简单，但无法覆盖真实工作流）。
- **重新评估**：用户实际报销单不再包含无票行。

## ADR-004 坐标锚点解析 + 金额三重校验

- **背景**：旧脚本按文本顺序正则，销售方 0/73、票号 7/73，金额靠取最大数兜底。
- **决定**：按词坐标找锚点最近值；金额用“小写 = 大写 = 金额 + 税额”交叉校验；低置信度显式标记。
- **替代**：纯正则（已证明不可靠）；云端结构化识别（隐私/成本）。
- **重新评估**：某票型坐标不可用（纯图片），退化为 OCR + 人工确认。

## ADR-005 文档与记忆机制

- **背景**：English-Lens 的 `PROGRESS.md` 已达 1128 行/88KB，读一次约 3 万 token；多处文档重复。
- **决定**：三层记忆（热 PROGRESS / 温 ROADMAP+docs / 冷 journal）；每个 PR 写 ≤15 行总结；文档有行数预算；单一事实来源。
- **替代**：单一大 PROGRESS（简单，但 token 成本随项目线性增长）。
- **重新评估**：文档拆分导致找不到信息（出现两次以上）时，合并或改索引。

## ADR-006 auto-pilot 暂不启用

- **背景**：English-Lens 有无人值守接力；本项目涉及财务数据与 UI 验证。
- **决定**：Phase 3 前不启用；需要时只用于范围明确、测试完备的机械任务。
- **重新评估**：黄金集 + CI 稳定，且任务可完全自动验证。

## ADR-007 分类口径以 `票据分类.doc` 为准

- **背景**：旧工具自创“材料设备”，与实际报销单的“其他费用”不一致。
- **决定**：默认 9 类；自定义类别可加，但导出时映射回报销单口径。
- **替代**：沿用旧工具分类（会造成对账困难）。
- **重新评估**：财务要求变更，或现有 9 类无法覆盖 10% 以上发票。

## ADR-008 多票页面先标记后拆分

- **背景**：少量 PDF 一页包含两张发票，直接按页解析会把两张票的字段串在一起。
- **决定**：Phase 1a 一页一条记录；检测到多个“发票号码/小写”锚点时标记“页面可能包含多张发票，需人工拆分”，不自动猜拆分。
- **替代**：按 y 坐标硬切（票面高度不固定，容易切错）。
- **重新评估**：Phase 1b 有足够多票样本后，做整页切分 + 每票独立解析。

## ADR-009 数据层与去重口径

- **背景**：需要重复导入不产生重复票、跨批次能查重、每张票可追溯，且金额不能有浮点误差。
- **决定**：SQLite；金额存整数分；`files.sha256` 整份去重；票号相同且开票日期/金额/销售方齐全并一致才算重复（跨批次跳过）；字段不一致或字段不全时两条都保留、互相标记冲突待确认，避免误删真实发票；无票号记录不猜测，入库并标记待确认；数据库默认 `data/invoicedesk.db`；`db.connect` 默认拒绝仓库内非忽略路径，以及 UNC、网络盘、OneDrive 等非本机存储（CLI `--force` 例外）；`data/` 内独立 `.gitignore` + 全局 `*.db` 忽略兜底。
- **替代**：JSON 文件（查询/并发差）；SQLite REAL 存金额（浮点漂移）；按文件名去重（改名即失效）；票号全局唯一索引（实测 780 份数据会误删 3 条多票页/冲突记录）。
- **重新评估**：单库超过 10 万张或需要多进程并发写入；多页/多票拆分改变“一页一票号”的假设；用户需要合并多个数据库。

## ADR-010 导出包：发票级 Excel + A4 二合一 PDF

- **背景**：数据层已就绪，但报销行属于 Phase 2；先交付可直接核对、打印和提交的发票证据包。
- **决定**：`export` 生成 `发票明细.xlsx`（明细/分类汇总/公司汇总/导出信息，含票型、低置信字段、待确认、警告；来源只写文件名+页码，警告里的本机路径导出前擦除）和 `发票二合一.pdf`（每 A4 两张唯一票面，带标签，待确认红字；缺源文件显式跳过；无可打印票面时覆盖为说明页，避免旧 PDF 混用）。筛选支持批次/购买方/开票日期/排除待确认，默认包含待确认；金额汇总按整数分；输出路径先解析再沿用数据层守卫（仓库内仅 `out/`、`data/`，拒绝网络盘/OneDrive，`--force` 例外）；两个产物先写临时文件再替换，写失败不破坏上一版。
- **替代**：按公司拆分独立文件（公司口径随 Phase 2 报销行明确）；导出绝对路径（会把本机目录带进提交件）；多票页自动拆分（ADR-008 仍先标记）。
- **重新评估**：Phase 2 报销行落地；财务要求固定模板或多公司分文件；黄金集显示多票页占比高。

## ADR-011 报销单模型与 Excel 版式

- **背景**：Phase 2a 要产出可提交的《费用报销支出明细表》；真实表含无票行、里程行、负向转账，且一行常对应多张发票（加油+高速）。各月模板列顺序还会变。
- **决定**：新增 `reports`/`report_lines`/`report_line_invoices`；金额整数分；一行 0..n 票；`has_invoice` + `invoice_note` 保留“有票（加油、高速）”写法；里程按 km×1.5 四舍五入到分，金额为准、km 仅元数据；`from-invoices` 每张未关联发票生成一行，已关联/缺金额/缺日期一律跳过并计数；三种版式 preset（project/company/plain），company 沿用 7 月表的 7 列标题合并；导出序号按插入顺序重排；用户输入文字不做 NFKC 折叠，发票来源文字保持解析器口径；导出守卫/临时替换与 ADR-010 同口径。
- **替代**：直接在用户 xlsx 模板上填值（列漂移、样式脆弱）；每张发票固定一行（ADR-003 已否）；无票行用备注模拟（无法汇总、无法校验）。
- **重新评估**：模板新增列或改成按行填公司；里程单价变化；需要一张报销单含多个报销人；财务要求保留人工序号。

## ADR-012 工作台前端：本地内置 Vue 单框架，Tabulator/ECharts 延后

- **背景**：Phase 2b 需要桌面工作台；ADR-001 计划 Vue 3 + Tabulator + ECharts，但当前数据量（≤1000 张发票、≤200 行）以筛选、勾选、行内编辑为主，尚无图表。
- **决定**：pywebview 6 JS bridge + Vue 3.5（`vue.global.prod.js` 本地内置，含 LICENSE，无 Node 构建）；用 Vue 自绘表格；票面用 PyMuPDF 渲染 PNG data URL；`app/api.py` 统一 ok/error 信封、每次调用独立 SQLite 连接并加桥接串行锁；页面 CSP 仅允许本地脚本/样式与 `data:` 预览图，`connect-src 'none'`（Vue 模板编译需要 `unsafe-eval`）；导入使用 GUI 线程原生文件夹对话框（ADR-016），粘贴路径继续可用；发票文本只做插值、禁用 v-html/innerHTML，Vue 版本与 sha256 记录在 `app/ui/vendor/SOURCE.txt`。
- **替代**：Tabulator（额外状态模型，排序/列固定暂不需要）；ECharts（看板只用单色 CSS 条形图，见 ADR-017）；HTML `<input type=file>`（WebView2 不暴露真实路径）；从桥接线程调用 `create_file_dialog`（非 GUI 线程，不安全）。
- **重新评估**：发票池 >5000 行或需要虚拟滚动/列固定时引入 Tabulator；看板需要多序列/交互图表时再引入 ECharts（当前单色 CSS 条形图足够）；pywebview 提供 GUI 线程回调后再做文件夹选择；Vue 改为预编译/运行时构建后可移除 `unsafe-eval`。

## ADR-013 发票字段人工修正、修正留痕与销售方规则学习

- **背景**：识别结果此前在界面只读，唯一修正途径是重新导入；护栏要求“每个识别结果可改、可追溯”，Phase 2b 的规则学习依赖人工修正信号。
- **决定**：新增 `invoice_edits`（字段/旧值/新值/时间）与 `category_rules`（销售方→分类）两表，schema v3 增量建表；工作台票面预览区可直接修改票号/日期/销售方/购买方/金额/分类/项目，票型保持只读；保存时逐字段写审计、把对应字段置信度置 high（清空置 low）；修正本身不解除待确认（仅在清空关键字段时重新标记），解除必须点“确认无误”，并写入一条 review 审计，避免改分类就掩盖冲突/多票页警告；识别警告与低置信记录始终保留；修正票号/日期/销售方/金额时在同一事务内重查同号记录，身份完全一致记重复、不一致记冲突、字段不全记无法确认，双方追加警告并重新待确认，不自动合并或删除；金额允许负数（红字发票），仅拒绝超过 ±10^15 分的离谱值；损坏的 warnings/confidence JSON 不回写、直接报错，避免静默清空；日期接受非零填充并统一存 ISO，校验错误只回显前 32 字符；xlsx 文本单元格统一强制 text 类型，防止 `= + - @` 等前缀形成公式；跨票警告给对端记录补 warning 审计，已确认记录被新冲突重新标记时补 review 审计；同名同值提交视为无操作；各文本字段设长度上限；销售方键做 NFKC + casefold + 去首尾空白（内部空格保留，避免“AB 公司”与“AB公司”合并）；人工改分类时 `category_rule` 记 `manual`，规则套用记 `learned.seller`，工作台显示“规则分类”软标记；分类修正立即记住一条按规范化销售方名称精确匹配的规则（`category_rule='learned.seller'`），导入时优先于内置关键词规则；同名同类的再次修正累加 `confirm_count`，改类则重置并覆盖，导入实际使用累加 `hit_count`；销售方为空不学习；规则只存本地库，已学规则不回溯修改库内历史发票，避免静默批改。
- **替代**：不做审计（无法追溯来源）；修正即自动解除待确认（改分类会掩盖冲突/多票页警告）；按项目/文件名学习（关键词噪声大）；累计 3 次才启用规则（错一次要等下批发票才发现，违背“修正一次即记住”）。
- **重新评估**：规则误判频繁时增加规则管理/停用界面或改为阈值生效；需要批量回溯时做成带预览与撤销的显式操作；财务要求票型也可改时再评估。

## ADR-014 分类规则管理：停用/删除与可审计回溯

- **背景**：ADR-013 让一次分类修正即可学习销售方规则，但不提供任何纠错入口：误学的规则会永久影响新导入，也无法把已确认的规则应用到此前导入的历史发票。用户需要能自救，同时不能让批量改分类变成静默改历史。
- **决定**：schema v4 给 `category_rules` 增加 `enabled`（旧库 ALTER 迁移，默认启用；迁移先于 SCHEMA 执行，便于后续 DDL 引用新列）；导入只应用启用规则；停用保留规则、可再启用，删除则移除规则，已分类的发票都保持原分类。规则页展示规范化销售方、分类、确认/命中/库内张数。修正一个已停用规则的销售方时只更新规则内容、保持停用——停用是用户显式选择，下一次修正不应静默恢复自动分类。回溯只对启用的销售方规则开放，先预览（命中、将更新、同分类、人工分类跳过、最多 20 条样例）并签发候选集凭证（规则更新时间、分类、候选 id 与当前分类/来源的 SHA-256）；执行在 `BEGIN IMMEDIATE` 事务内重读规则与候选、重新计算并校验凭证，任何数据变化都拒绝并要求重新预览，避免写入范围或前值超出确认文案、也避免与另一连接的人工修正竞态；执行时跳过 `category_rule='manual'`（人工分类是更强的信号）与已是目标分类的记录；每条变更写 `category` 审计，分类来源变化时另写 `category_rule` 审计，置 `category_rule='learned.seller'`、分类置信度 high，但不改待确认标记与识别警告；整批一个事务，置信度 JSON 损坏时整批回滚。删除规则不改历史发票的 `category_rule` 来源标记。规则页与确认文案对销售方/分类按 Unicode 类别（Cc/Cf/Cs/Co/Zl/Zp）清洗控制与格式字符，并按码点限长，避免不可信票面文字伪装确认信息。
- **替代**：只允许删除（误删后无法复用）；修正时自动重新启用规则（覆盖用户的停用决定）；回溯时一并清除待确认（会掩盖冲突/多票页警告）；提供“撤销整批回溯”（当前用逐张修正记录追溯，尚未需要）。
- **重新评估**：规则误判频繁或需要按发票覆盖规则时引入规则优先级/阈值；回溯被要求批量撤销时增加批次审计与撤销；规则量超过数百条时再考虑分页与搜索。

## ADR-015 CI 触发精简：代码/文档分流，取消 main 重复跑

- **背景**：私有仓库的 Actions 分钟数有限，Windows runner 按 2 倍计费；2026-10-28 账户因账单/额度问题直接拒绝启动 job。原 CI 在每个代码 PR 跑 Windows 全量 + Linux 工具测试，合并到 main 后再跑一遍，docs-only PR 也会跑 Windows 全量。
- **决定**：`ci.yml` 只在 `pull_request` 的代码路径（app/tests/tools/pyproject/requirements/自身）运行，Windows 全量仍是合并门槛；删除 `push: main` 与文档路径触发，避免每次合并重复计费；新增 `docs.yml` 在 ubuntu 上只跑 `tests/test_project_hygiene.py`（预算/隐私/忽略规则），文档 PR 不占 Windows 分钟；保留 concurrency 取消旧运行，并提供 `workflow_dispatch` 手动全量。AI 审查的路径本来就不含文档。
- **替代**：全量测试改 ubuntu（未验证跨平台，暂保留 Windows）；docs 路径完全忽略（会丢预算/隐私检查）；只在 main 上跑 Windows（失去 PR 门禁）。
- **重新评估**：跨平台验证通过后，可把全量套件移到 ubuntu、Windows 只跑 smoke；若额度仍紧张，改为标签/手动触发 Windows 全量。

## ADR-016 文件夹选择：WinForms GUI 线程原生对话框 + 依赖注入

- **背景**：工作台导入原先只能粘贴路径。pywebview 把 JS 桥接调用派发到 worker 线程，而 WinForms 对话框必须在拥有窗口的 GUI 线程创建；pywebview 6.2.1 也没有 JS 侧的文件/文件夹对话框 API。
- **决定**：`Api` 构造时注入 `folder_dialog(current) -> str | None`，API 层不 import pywebview；`app.main.make_folder_dialog` 通过 `window.native.Invoke(System.Action(...))` 把 `window.create_file_dialog(FileDialog.FOLDER, initial)` 排到 GUI 线程，等待 600 秒，取消返回 `None`，异常统一转成可读错误。初始目录优先用当前输入（存在时），否则用用户主目录；`pick_folder` 端点裁剪超长输入，返回 `{"path": ...}`，错误走统一信封并被 `redact_paths` 擦除。导入弹窗新增“浏览…”，粘贴路径继续可用；按钮在选择期间禁用。
- **替代**：应用内目录浏览器（代码多、交互差）；tkinter 对话框（第二套 GUI 工具包）；HTML `webkitdirectory`（只给文件、拿不到目录路径）；在桥接线程直接调用 `create_file_dialog`（线程限制，已知失败）。
- **重新评估**：pywebview 提供官方 GUI 线程调度或 JS 对话框后移除 `Invoke` 依赖；需要多选/最近目录记忆时再扩展。

## ADR-017 汇总看板：后端聚合 + 单色 CSS 条形图，不做云端图表

- **背景**：Phase 2b 需要一张能回答“这个月花了多少、花在哪、哪些票还没处理”的看板；当前数据量 ≤1000 张，单一金额序列，ECharts 与本地 HTTP 源都会扩大攻击面与依赖。
- **决定**：`workbench.dashboard_summary` 对与发票池完全相同筛选条件下的 `InvoiceRow` 做纯 Python 聚合（无新 SQL、无缓存），输出合计、待确认、低置信、缺金额、缺源文件、已修正、未关联、分类分布、月度分布；缺金额的票计入张数但不计入金额，分类/月度保留零金额行；无日期归入“未知日期”并排在最后；分类按金额降序、同名按张数；`Api.dashboard` 复用 `_invoice_filters`，无效日期或倒序区间走统一信封。界面为弹窗：一个主数字、KPI 磁贴、分类/月度单色横向条形图；条宽按绝对值归一（负数仍显示带符号金额），每行直接标注金额与张数，`title` 提供悬停信息；金额列表本身可当表格读，不引入图例/双轴；额度提示需要月度收入录入，归入 Phase 4。
- **替代**：前端从已加载行聚合（无法单测、与后端口径易漂移）；ECharts（单序列收益低，违反本地 CSP 精简原则）；把额度提示塞进看板（必须先录收入，增加报账步骤）。
- **重新评估**：出现多序列/交互图表需求或发票池 >5000 行时引入图表库与虚拟滚动；有收入录入后把费用额度占比接到同一看板。

## ADR-018 外观与快捷键：data-theme 先行 + 最大窗口，按本机 DPI 兜底

- **背景**：需要手动深色开关与常用操作快捷键；本机 1280×720 逻辑屏、150% DPI 下，固定 1440×900 窗口被 Windows 钳制，而 WebView2 仍按较大视口排版，右侧工具栏被裁切。
- **决定**：新增 `theme.js`，在样式表之前同步解析 auto/light/dark，把结果写到 `<html data-theme>`；auto 监听 `prefers-color-scheme`；手动模式尽力写入 `localStorage`（`private_mode` 可能清空，故不承诺跨启动持久化），存储异常不影响会话内切换；CSS 只有 `:root[data-theme="dark"]` 一套深色 token，不再重复媒体查询。快捷键挂在 document：Esc 关闭最上层弹窗/票面；Ctrl+K 聚焦搜索、Ctrl+I 导入、Ctrl+E 导出、Ctrl+B 显示/隐藏发票池、Ctrl+D 汇总看板、Ctrl+Enter 保存票面修正、Ctrl+Shift+D 循环外观、F1 帮助；弹窗打开时动作快捷键不触发，Esc 与外观仍可用，F1 只在无弹窗时打开帮助。主窗口改为 `maximized=True`（默认 1200×800，最小 1024×640），由系统工作区决定实际尺寸，避免 WebView 视口大于窗口。
- **替代**：把外观存进数据库设置表（为单个 UI 偏好加 schema 迁移）；仅跟随系统（不满足手动开关）；保留固定窗口（小屏裁切工具栏）；给快捷键做全局注册（WebView2 无此需求）。
- **重新评估**：用户要求外观跨启动保留时增加 settings 表；pywebview 修复 Windows DPI/窗口尺寸映射后可去掉最大化兜底；快捷键与输入法/浏览器冲突时再调整组合。

## ADR-019 打包运行位置、日志与启动防护

- **背景**：Phase 2 只有源码运行；给非开发用户需要双击 exe。安装目录可能只读且升级会整目录替换；窗口版没有控制台，启动失败不可见；目标机器可能缺少 WebView2。
- **决定**：PyInstaller 用 one-dir（启动快、不必每次解压），UI 作为 datas 放到 `app/ui`，`runtime.resource_path` 兼容 `_MEIPASS`。冻结态默认根目录 `%LOCALAPPDATA%\InvoiceDesk`（`invoicedesk.db`、`out\`、`logs\`）；源码态保持 `data/`、`out/`。`INVOICEDESK_HOME` 覆盖根目录，`INVOICEDESK_DB` / `INVOICEDESK_OUT` 单独覆盖；所有路径仍走 `db.connect` 与 `output_path_reason` 守卫。日志用 RotatingFileHandler（1 MB × 3），冻结态 stdout/stderr 为 None 时重定向到日志；sys/threading excepthook 记录异常并按需弹窗。启动前只读注册表查询 Evergreen WebView2 GUID；缺失则 MessageBoxW 给出下载地址并返回 2，`create_window`/`start` 失败同样弹窗并写日志；不自动联网下载。`--smoke` 用临时库检查 UI 资源、WebView2 与 bootstrap 版本，构建脚本据此判定失败。图标由标准库 `tools/make_icon.py` 绘制多尺寸 ICO，不引入 Pillow。
- **替代**：one-file（每次启动解压慢、临时目录更大）；数据放安装目录（只读/升级丢数据）；只靠控制台报错（窗口版看不到）；自动下载 WebView2（联网行为未授权）；Pillow 画图标（为一张图增加依赖）。
- **重新评估**：需要绿色便携版时把 `INVOICEDESK_HOME` 指到 U 盘；改为固定版本 WebView2 分发时补充检测；构建体积/时间影响发布时再评估 UPX 或裁剪依赖。

## ADR-020 图片/扫描发票：随包本地 OCR（RapidOCR + ONNX），识别结果显式待确认

- **背景**：真实 2026-10 批次中有 10 张 PDF 是纯图片（无文本层），现有解析器只能标“扫描件”，用户要求“不管什么原因都要识别”。财务数据不能上云，OCR 必须离线、随程序分发。
- **决定**：引入 `rapidocr-onnxruntime`（PP-OCRv4 检测/识别/方向模型，约 16 MB 模型 + onnxruntime/cv2），首次使用时懒加载；把页面以 200 DPI 渲染成灰度图 OCR，按 PDF/像素比例把四点框映射回 `TextLine`，直接复用现有几何解析器（票号、日期、买卖方、金额三重校验、项目、分类）。OCR 页追加“票面无可用文本层，已用 OCR 识别，请核对”警告，所有字段置信度最高为 medium，记录进入待确认；源文件仍只读。红章覆盖标题导致缺“普通”时，以“电子发票 + 发票号码”兜底票型；OCR 把买卖方税号行合并成一行时按左右顺序配对，并按“购买方/销售方”标签或列位置决定买卖方，避免行高差互换。旧库记录用 `reparse_unrecognized` 原地重识别：跳过有 `invoice_edits` 的记录与缺源文件，遇到同号只标记冲突、不删除；工作台有“重新识别未识别”入口。PDF 文本层存在但被 CID 字体弄乱（汉字 <8 且页面有图）时也走 OCR。`rapidocr-onnxruntime` 1.4.x 要求 Python <3.13，因此项目最低版本改为 3.11、CI 改跑 3.12（打包仍用 3.11）。
- **替代**：Windows.Media.Ocr（依赖系统 OCR 语言包，跨机器不可控）；Tesseract（需外置 exe + 语言数据，分发更麻烦）；云端 OCR（违反数据边界）；只靠二维码（拿不到买卖方/项目）。
- **重新评估**：低清/拍照发票准确率不足时，升级到更大 PP-OCR 模型或增加图像预处理；one-dir 包体（约 240–275 MB）成为分发障碍时，评估按需下载模型（需联网授权）或 Windows OCR 后备；识别速度（约 5 秒/页）成为瓶颈时再评估并行/更小模型。

## ADR-021 常用文件夹/表头记忆、导出汇总与大写、导入导出入口

- **背景**：每次导入都要重新选文件夹；公司/部门/报销人重复输入；导出表缺少分类小计、总计与大写金额；导入/导出按钮混在次要操作里不便找。
- **决定**：schema v5 新增 `settings(key,value)`，最近导入文件夹存 JSON 列表（大小写不敏感去重、最多 8 个、仅展示仍存在的目录），`pick_folder` 选中即记、`import_folder` 成功再记；bootstrap 返回该列表，导入弹窗预填并提供一键填入。公司/部门/报销人不另存 settings：`db.report_choices` 从 `reports` 表按使用次数取前 20，前端用 datalist + 常用 chips，新建表单沿用当前/最近一张报销单的值。导出统一加中文大写：`amounts.chinese_upper(_cents)` 按财务规则处理零、角、分、万/亿；报销单明细第 3 行与末行合计写入大写并新增“分类汇总”sheet（行数/金额/占比/合计/大写），证据包明细、分类汇总、导出信息同步加大写。顶部把“导入发票”和“导出（报销单/证据包）”做成彩色主按钮，其余（汇总/规则/外观/帮助）收进“更多”菜单，保留 Ctrl+I/Ctrl+E/F1。
- **替代**：把 UI 偏好放 localStorage（`private_mode=True` 不跨启动）；每次从最近的导入批次推导（会漏掉未导入/已清空文件夹）；用第三方大写金额库（几十行可测代码，避免新依赖）。
- **重新评估**：需要跨设备/跨用户同步常用值时改为导出/导入设置文件；报销单模板要求大写写在其他行时按模板调整；顶部空间更紧张时把“新建报销单”也收进菜单。

## ADR-022 按公司/分类输出无标签合并 PDF

- **背景**：财务提交要求“每个公司下面每个分类一个 PDF”，而现有 A4 二合一打印 PDF 带序号/日期/金额标签，适合审计、不适合提交；真实 10 月批次含 7 个公司×分类组合。
- **决定**：新增 `app/core/group_pdf.py`，按 `buyer_name` + `category` 分组，每组只把唯一 `(source_path, page_index)` 原样嵌入新 PDF：不写任何文字、不加封面、保留源页尺寸（输出尺寸后由 ADR-024 改为 A4 二合一）；输出 `out/export/发票分组/<公司>/<分类>.pdf`，文件名清洗 Windows 非法字符与保留名。空购买方依次用“筛选结果中唯一购买方 → 当前报销单公司（唯一模糊匹配）→ 未识别购买方”兜底；空分类归“未分类”。同组同页去重，跨组各出一份。每次导出按 `.manifest.json` 只删除上次生成的 PDF，用户手放的文件不动；缺源/损坏页跳过并在结果中报告。证据包与 CLI `export` 一键同步生成；2-up 审计 PDF 保留标签不变。
- **替代**：继续用带标签的 2-up（用户明确拒绝）；每张票一个 PDF（文件过多）；一个 PDF 内按书签分组（财务仍需拆分）；按上级目录名猜公司（同一根目录下可能混有两家公司的票据，会误归）。
- **重新评估**：财务需要封面/目录/书签时再加；同一票面跨分类必须只出现一次时改为“主分类 + 引用清单”；公司口径改为报销单而非购买方时按报表分组。

## ADR-023 旧扫描记录自动补识别，审计行不阻塞 OCR

- **背景**：3c 上线后，旧库 10 条扫描记录仍为 `scanned`：它们由无 OCR 的旧版本导入，文件 hash 去重使重复导入直接跳过；用户点过“确认无误”，`invoice_edits` 里只有 `review` 审计行，而 `reparse_unrecognized` 把所有有编辑记录的发票都当作人工修正跳过，结果 10/10 无法补识别。
- **决定**：`reparse_unrecognized` 只在存在**字段**修正（`field NOT IN ('review','warning')`）时跳过；“确认无误”只是审计，不保护识别结果。`import_folder` 对本次扫描到的、已在库中且类型为 `scanned/unknown/error` 的文件 hash 自动重跑 OCR，导入摘要返回候选/成功/失败数；OCR 不可用时直接跳过。bootstrap 返回未识别总数，工作台顶部提示条可一键重识别，发票池新增“仅未识别”筛选。
- **替代**：启动时全库自动重识别（耗时不可控、CPU 峰值）；把 `review` 当字段修正（即当前缺陷）；删除记录后重新导入（可能丢人工修正与关联）。
- **重新评估**：若某些文件每次导入都 OCR 失败并拖慢导入，增加失败标记与退避；OCR 支持并行/取消后把补识别放进后台任务。

## ADR-024 分类 PDF 改 A4 二合一（更新 ADR-022 的输出尺寸）

- **背景**：按原页尺寸合并的分类 PDF 打印大小不一，A4 打印要么缩放要么留白；财务要求“每页两张票、各占一半、无标签”。
- **决定**：`group_pdf._merge_group` 每张 A4 上下两个槽位，源页等比缩放嵌入（A4 595.276×841.89、边距 16、间隔 6，与审计 2-up 同参数但不留标签行），槽间画 0.4pt 浅灰分割线；仍不写任何文字。`GroupPdfFile.pages` 改为 A4 张数，新增 `source_pages` 记录票面页数，CLI/UI 同步显示。
- **替代**：继续原页尺寸（用户明确要求 A4）；直接复用带标签审计版（标签不适合提交）；每页单张 A4（费纸）。
- **重新评估**：财务反馈缩放后小字不可辨时改每页一票或横向排布；需要可搜索文本时评估叠加 OCR 文本层。

## ADR-025 内置分类规则版本化回填（旧库自动重分类）

- **背景**：分类在导入时落库；酒店「餐饮服务」改判餐饮费的规则修复只影响新导入，旧库行仍停在差旅费，导出 PDF/Excel 继续错分。
- **决定**：`categories.RULES_VERSION` 随内置规则变更递增；`db.init_db` 调 `recategorize.refresh_builtin_categories`，在 `settings` 记录已应用版本，每版本只扫一次。仅重算 `category_rule` 为 `seller.*`/`item.*`/`fallback` 的行；`manual`（人工改类）与 `learned.seller`（学习规则）保持不动。分类变化写 `invoice_edits` 的 `category_refresh` 行（不算“人工修正”，不计入工作台已修正、不阻塞 OCR 重识别）。重算只用库内 seller/item/文件名，不再解析源文件。
- **替代**：导出时临时重算（工作台与导出不一致）；导入时全库重算（每次导入变慢）；直接 SQL 批量改（无审计、可能覆盖人工分类）。
- **重新评估**：规则频繁小改导致版本扫库成本明显时，按规则 id 记录更细粒度版本；需要保留历史分类口径时增加“按批次规则版本”维度。

## ADR-026 分类 PDF 金额命名与公司总合并（更新 ADR-022/024 的产物结构）

- **背景**：财务需要不打开文件就能核对分类金额；提交时希望每个公司一份按分类顺序排列的完整 PDF。
- **决定**：分类文件命名 `<分类>-<价税合计>元.pdf`（金额取该组记录合计，整数分转两位小数，经 `_safe_name` 清洗）；每个公司另出 `总合并-<合计>元.pdf`，按 `CATEGORIES` 顺序拼接已生成的分类 PDF（不是重新排源页），跨公司不合并以免混淆购买方；manifest 同时清理两类产物。API/CLI 返回每组金额与合并文件信息，UI 导出清单列出总合并文件。
- **替代**：总合并跨公司（提交时混购买方）；按源页重排（分类边界可能同页两张）；只命名不合并（财务仍要逐类打开）。
- **重新评估**：财务要求一个全批次总 PDF 时可加可选的“全部公司合并”；分类金额要求按唯一票面而非记录合计时调整计价口径。

## ADR-027 待确认队列与「本月报账」向导（只编排，不改确认语义）

- **背景**：3d 后库里仍有大量待确认票，用户要在发票池里反复筛选、点开、返回；ROADMAP 3e 要求月度报账 ≤15 分钟，且核对路径可只用键盘。
- **决定**：队列用 `review_only` 按当前批次/日期取快照，确认后本地移除条目，不改发票池筛选；撤销确认实现为 `reopen_invoice`（`needs_review=1` + `review` 审计行），保留可追溯；“本月报账”向导只编排现有端点（import_folder/dashboard/list_invoices/create_report/add_lines_from_invoices/export_report/export_evidence），不新增批量写接口；向导内核对时隐藏向导，队列退出或预览关闭回到第 2 步。
- **替代**：队列复用 `include_review` 过滤（会被搜索/未关联等条件干扰）；撤销只做界面回退（库里仍是已确认，刷新即丢）；向导新增批量接口（重复实现且绕过审计）。
- **重新评估**：队列在多千行仍卡顿时改为只取 id、按需 `get_invoice`；需要整批回滚时改为会话级事务日志。

## ADR-028 数据库滚动备份与显式恢复

- **背景**：数据库是发票池的唯一副本（Excel/PDF 都能重导出，人工修正、分类规则、报销单不行）；3e 向导把“批量确认、一键成行”变成几次点击，误操作代价变大；此前没有任何撤销或恢复入口，换机/重装即丢库。
- **决定**：新增 `app/core/backup.py`。快照放在数据库同目录的 `backups/`（继承本机/固定盘守卫，不上云），用 SQLite backup API 生成一致副本：先写 `<名>.tmp`、校验 `integrity_check` 再 `os.replace`，不会把半成品当备份；文件名 `<库名>-YYYYmmdd-HHMMSS-<原因>.db`，同一秒再生成时追加 `-2`/`-3` 后缀而不是覆盖前一份；只列出/清理/允许恢复自己命名的文件，用户放进目录的其他文件一概不动。触发点：启动前（`main.prepare_database`，空库跳过，失败只记日志、绝不阻塞启动）、导入有新文件后（失败不影响导入结果）、手动、恢复前；滚动保留 10 份。恢复只能从备份目录内、按列表校验过的名字进行；候选必须先通过 `integrity_check` 且 `user_version` 不高于当前程序；恢复前把当前库另存为 `pre-restore`（SQLite 读不了时退化为字节复制，坏库也留档）；用同目录 `.restore` 临时文件 `os.replace` 原子替换，并删除旧 `-wal/-shm` 防止把旧日志回放进新库。启动时数据库打不开用原生 Yes/No 询问是否用最近备份恢复；另一个实例占用（locked/busy）不触发恢复。工作台“更多 → 数据备份…”提供列出、立即备份、恢复、打开目录；恢复成功后重载工作台并清空预览缓存（行 id 全变）。
- **替代**：靠用户自己导出 Excel 当备份（不含人工修正、规则与报销单）；定期 zip 整个数据目录（含日志与本机路径，体积大且难定位）；自动恢复不询问（可能用旧备份覆盖更新的数据）；复制到 U 盘/网盘（越过“只在本机”的红线，需要用户显式操作）。
- **重新评估**：库增长到数百 MB 时改为增量备份或按天保留；用户要求指定备份盘时加“备份目录”设置（仍须过本机守卫）；恢复后工作台重载变慢时改为增量刷新；需要防勒索/带版本历史时再评估多代快照。

## ADR-029 重复票审查：按票号聚合，归档而不是删除

- **背景**：导入、人工改票号、OCR 重识别都会让同号记录双保留；真实库 225 条里有 6 组同号记录，其中 7 月历史数据在重识别后出现多组完全重复。此前只能在发票池逐条看，没有“只留一张”的入口，781 行里人工对齐成本高。
- **决定**：schema v6 增加 `archived_at`（默认空）。`workbench.list_conflict_groups` 把非空票号的**有效**记录聚合；日期/金额/销售方完全相同的标“重复票”，否则标“同号冲突”。`invoices.resolve_conflicts` 保留选中一张，其余写 `archived_at` 并清掉冲突类警告（`CONFLICT_WARNING`/`DUPLICATE_WARNING`），双方各写审计行（`archive`/`conflict`）；记录不删除、源 PDF 不碰，`restore_invoice` 可恢复并在仍有同号时重新双标冲突。归档列表与恢复放在同一审查弹窗。所有默认读路径排除归档：发票池、看板、批次统计、导出/证据包/分组 PDF、未关联生成行、规则回溯与销售方计数、重识别、导入去重索引。已关联报销单的记录拒绝归档；解决冲突不等于确认，保留的记录仍需显式确认。
- **替代**：物理删除重复记录（不可恢复，违反可追溯）；连同源 PDF 删除（越过源文件只读红线）；只在导入时自动跳过（历史 6 组无法处理）；强改票号去重（票面与记录不一致）。
- **重新评估**：需要“归档 N 天后自动清理”时再加设置；分类/导出口径要求包含全部历史记录时改为纯标记视图；归档量导致列表卡顿时改为分页或按票号搜索。

## ADR-030 导入预检与后台导入任务（可取消）

- **背景**：全量 767 个文件导入约 27 秒，图片发票 OCR 可达数分钟；此前导入是一个同步桥调用，界面只有静态“请稍候”，用户不知道进度也无法中止，误选大文件夹只能退出程序。
- **决定**：核心层拆成 `plan_import`（扫描、哈希、去重判断、OCR 页数估算，只读）与 `execute_plan`（单事务写入）。`import_preflight` 返回“新增 N / 重复 M / 预估 OCR K 页 / 补识别 X 张”和 15 分钟内有效的一次性 token；`import_start` 用 token 复用计划，在后台线程用自己的 SQLite 连接执行；`import_status` 只读内存状态供 UI 每 400ms 轮询；`cancel_import` 置取消标志。取消发生在写入事务提交前 → 抛 `ImportCancelled` 并整体回滚（不产生空批次/半批数据）；提交后的旧记录补识别按行提交，取消只停止后续重试，汇总标 `cancelled`。OCR 按文件粒度检查取消。`db.connect` 增加 `busy_timeout=5000`，让后台写事务期间的状态读取与短查询等待而不是报 locked。导入弹窗改为“预检 → 确认导入 → 进度条/取消”；向导直接启动并复用同一进度条。
- **替代**：同步桥调用 + 假动画（无法真取消）；WebSocket/SSE 推送进度（pywebview 无此通道，轮询足够）；每导入一张就提交（取消可保留部分结果，但会产生半批数据，破坏“一次导入=一个批次”的可追溯性）；把预检也做成后台任务（大文件夹预检仍是一段不可取消的扫描，但预检只读，取消收益低）。
- **重新评估**：预检在 700+ 文件上超过 1 分钟时改为后台预检；需要应用关闭时安全中断（当前 daemon 线程随进程退出，事务回滚）；出现并发导入需求（多窗口）时改为队列。

## ADR-031 首次启动向导：数据目录写进外部配置，空库才可切换

- **背景**：Phase 3b 要求干净 Windows 机器上双击即可用，并支持重装后继续用原数据。数据库位置此前固定为程序目录（打包版 `%LOCALAPPDATA%\InvoiceDesk`，源码版 `data/`），用户不能把库放到自己的固定盘；换机/重装只能手动拷 `invoicedesk.db`。同时首次打开没有任何说明，用户不知道源文件只读、OCR 在本机、导入要选文件夹。
- **决定**：新增 `app/core/appconfig.py`，在“应用目录”而不是数据库里保存 `config.json`（打包版 `%LOCALAPPDATA%\InvoiceDesk\config.json`，源码版 `data/config.json`），只存 `data_dir` 与 `welcome_done` 两个字段；写入用临时文件 + `os.replace` 原子替换，文件缺失/损坏一律按空配置处理。取址优先级：`INVOICEDESK_DB`/`INVOICEDESK_OUT` 环境变量 > 配置里的 `data_dir` > `INVOICEDESK_HOME`/打包默认或源码默认；数据库、导出目录、日志三者一起跟随。首次向导只在 `welcome_done` 为空且库内没有批次、没有报销单时出现（`bootstrap.first_run`）；`select_data_dir` 同样只允许空库调用，校验绝对路径、本机固定盘（复用 `remote_storage_reason`）、不在仓库内（`data/`、`out/` 除外），建目录并写入探针文件；目标里已有 `invoicedesk.db` 时先用只读连接检查版本、表结构与发票/批次/报销单计数，确认为本软件的库才“接管”（这是重装、换机恢复原数据的路径）。空库文件不算已有数据，仍提示“将在这里新建”。向导不移动、不复制任何已有数据；已有数据的用户不会看到数据目录步骤。首次向导不能靠 Esc/点遮罩关闭，必须在最后一步完成或显式“跳过”；“更多 → 首次使用向导”可重新查看导入说明（不再出现数据目录步骤）。手工编辑配置文件属于本地用户自己的选择：运行时仍由 `db.connect` 复核本机固定盘与仓库边界，打开时校验版本与表结构；“仅空库才能切换”是界面流程约束，不是数据安全边界。
- **替代**：把设置存进 SQLite（先有库才能读库，鸡生蛋）；选新目录时自动搬库（跨盘复制/删除用户数据，风险高且无确认）；每次启动都显示向导（噪音）；用开窗前的原生对话框选目录（无法说明隐私与导入流程）；允许有数据时切换目录（旧库被静默遗留，产生“数据消失”错觉）。
- **重新评估**：用户需要“把现有库迁到新盘”时，增加显式的复制 + 校验 + 切换流程（仍不删除源库）；出现配置丢失导致误用默认目录时，把配置一并纳入备份或提供“找回数据目录”引导；需要便携模式时开放配置路径环境变量，而不是改配置格式。

## ADR-032 打包版数据目录跟随首次导入文件夹

- **背景**：打包版把库/备份/导出/日志放在 `%LOCALAPPDATA%\InvoiceDesk`（C:），而发票常在 E: 等数据盘；用户要求保存位置不要落在 C 盘、改为导入发票所在的文件夹。ADR-031 的“重新评估”已预判“把现有库迁到新盘”需要显式流程。
- **决定**：`runtime.uses_app_home()`（打包版或 `INVOICEDESK_HOME`）且 `data_dir` 未固定、库为空时，`import_start` 在写库前把数据目录定为 `<首次导入文件夹>/InvoiceDeskData`，原子写 `config.json` 后再启动后台导入；`import_preflight` 只读返回 `data_dir_preview`，确认弹窗先告知保存位置；首次向导不再预选 C: 应用目录，改成“跟随发票文件夹（默认）/指定固定目录”两条路；源码运行仍用仓库 `data/`，不受影响。既有库用 `app/core/datamove.py` 与 `tools/migrate_data_dir.py`：SQLite backup API 复制、校验完整性/版本/行数与金额总额、更新配置，源库保留不删。护栏放宽为“只允许在首次导入的发票文件夹下自建 `InvoiceDeskData/`，源 PDF 与源目录其他位置不动”。
- **替代**：每次导入都换一套库（跨批去重、同号冲突、看板统计全部失效）；放在发票文件夹上一级（不满足“放在发票文件夹内”）；后台自动搬库不确认（跨盘复制与删除风险）；只改导出目录（库和备份仍在 C 盘）。
- **重新评估**：从网络盘/OneDrive 导入时路径守卫会跳过接管（库留默认），需要时再加“另存数据目录”提示；真的出现多库并行需求时再改配置格式；迁移时无法可靠检测应用是否仍在运行，改为锁文件机制后再评估。

## ADR-033 v1.0 版本信息与 README 截图

- **背景**：Phase 3b 以“README 截图、版本信息、v1.0”收尾。此前版本号停在 0.1.0，只出现在代码常量与界面角标；打包后的 EXE 文件属性没有版本；发布说明也没有界面图，用户只能看文字判断装的是哪一版。
- **决定**：`pyproject.toml` 的版本是唯一来源，测试断言 `app.__version__` 与之相等；`tools/make_version.py` 读取它生成 PyInstaller 版本资源 `build/version_info.txt`，`build_app.py` 每次构建前重建，EXE 属性页显示同一版本；“更多 → 关于发票管家…”显示版本、运行方式（打包/源码）、数据目录、数据库文件与 schema，`bootstrap` 只增加 `database_version`、`frozen` 两个只读字段。README 截图用合成发票在真实 WebView2 窗口里驱动抓取，只提交 `docs/images/` 下四张界面图，不含真实发票或本机路径；关于弹窗截图含临时数据目录，不对外发布。
- **替代**：手写版本资源（与代码漂移）；EXE 属性留空（用户无法判断版本）；用 mock 页面截图（可能与真实界面不一致）；用真实库截图（财务数据只在本机的红线）。
- **重新评估**：需要多语言版本属性时改版本资源字符串表；界面大改后按 `docs/journal/2026-10.md` 记录的流程重拍截图。

## ADR-034 数据与导出分离：发票文件夹只留「报销发票整理」

- **背景**：ADR-032 让打包版把库/备份/导出/日志一起放进发票文件夹下的 `InvoiceDeskData`。实机使用后，该文件夹混着数据库、日志和导出文件，用户难以辨认；归档或同步发票文件夹时，财务库也会被一起带走。
- **决定**：数据目录只放 `invoicedesk.db`、`backups/`、`logs/`，打包版默认 `%LOCALAPPDATA%\InvoiceDesk`，首次向导仍可固定；导出目录独立，由 `config.json` 的 `export_dir` 记录，导入预检展示、确认后把导出切到 `<发票文件夹>/报销发票整理`，明细、报销单和 PDF 直接放在该文件夹内（不再套 `export/` 或 `report/` 子层），只写生成文件。显式传入 `out_dir` / `INVOICEDESK_OUT` 时不跟随。`报销发票整理` 与旧 `InvoiceDeskData` 都加入扫描跳过目录，防止导出 PDF 被再次导入。旧版数据用 `tools/split_data_dir.py` 复制库/备份/日志回应用目录、把旧 `out` 复制到 `报销发票整理` 并更新配置，旧目录不删。
- **替代**：保留 `InvoiceDeskData` 只改内容（用户仍以为里面有库，归档时连库一起搬）；导出也放回应用目录（用户找不到成果）；启动时自动迁移旧目录（运行中移动库无法保证安全）。
- **重新评估**：如果导出需要按批次而非“最近导入文件夹”归档，改为导出时选择目录；如果用户明确要求库随发票文件夹走（移动盘场景），把 ADR-032 的跟随方式恢复成显式选项。
